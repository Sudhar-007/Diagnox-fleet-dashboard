# Hardware <-> Software Interface

## Hops
1. ESP32-WROOM + EC200U (4G) + GPS + OBD-II -> dashboard BFF over HTTPS (4G). Device side owned by hardware teammate.
2. Device push: `POST https://diagnox-fleet-bff.onrender.com/api/telemetry` (`dashboard/server/routes/telemetry.js`, checks in `services/telemetry.js`).
   - Headers: `Content-Type: application/json` and `x-api-key: <TELEMETRY_API_KEY>` (shared secret set in the BFF environment, never in git).
   - Body: one telemetry object (below) or a JSON array of up to 300 of them (backlog after a 4G outage), at most 512 kB. Points may arrive in any order; the BFF sorts them by `timestamp` and runs every point through alerts, SOS, collision, trips, driver events and fuel one at a time, oldest first (yielding to other work every 25 points; concurrent requests are processed one after another). Alerts and SOS are judged against the truck's newest stored point, so the device must send queued points oldest first and drain its backlog before sending new live points: a backlog point older than a point already received is stored but not judged.
   - Each point: `truck_id` string of 2 to 16 letters, digits or dashes (case-sensitive, not trimmed); `timestamp` exactly `YYYY-MM-DDTHH:MM:SS` (local time, no zone suffix; a `Z`, offset, fraction or date-only value rejects the point, since it would be read hours off under the BFF's `TZ`), not more than `rules.ingest.max_past_s` (86400 s, 24 h) before the BFF clock (an unset device clock is rejected with a message asking about it). `truck_id` must not be one the simulator drives (TN01 to TN05 in `hybrid`), so real and simulated readings never mix on one truck; register the device's id in Vehicles. The six sensor fields are required, each a JSON number or a numeric string (optional `-`, digits, optional `.digits`, surrounding spaces allowed; no exponent, no `+`, no bare `.5`), within inclusive sanity bounds (coolant_temp and oil_temp -40 to 200, battery_voltage 0 to 40, rpm 0 to 10000, engine_load 0 to 100, speed 0 to 300; `rpm` is not required to be a whole number). `latitude`/`longitude` are numbers, numeric strings or null/missing; any other value rejects the point. Both are stored as null (no GPS fix) when either is null/missing, latitude is outside -90 to 90, longitude outside -180 to 180, or both are exactly 0. Numeric strings are stored as numbers. Optional `fuel_level` and `maintenance_risk_score` are kept (as numbers) only when they are a number or numeric string, with no range check here, otherwise dropped; `sos` is stored as `true` for `true`, `1`, `"1"`, `"true"` and `false` for `false`, `0`, `"0"`, `"false"`, otherwise (including null) dropped. Every other key is dropped, so a device cannot set derived fields.
   - Responses: `200 { accepted, ignored, rejected: [{ index, error }] }` when at least one point was valid (`accepted`: points the store kept; `ignored`: valid but not stored, i.e. a repeated `timestamp` for that truck, stamped more than `rules.ingest.max_future_s` (300 s) ahead of the BFF clock, older than every point held when the truck's 5000-point buffer is full, or a server error while storing; `rejected`: invalid points, `index` is the 0-based position in the request (0 for a single object), `error` a short reason); `400` same body when no point was valid, or `{ error }` for a malformed body (invalid JSON, not a JSON object or array, an empty array, or a missing/non-JSON `Content-Type`, which leaves the body unread); `401 { error }` missing or wrong key; `413 { error }` more than 300 points or a body over 512 kB; `503 { error }` device data off (`TELEMETRY_API_KEY` unset or blank; or, for a caller with the right key, `DATA_SOURCE=mock` or an unknown value). Checks run before the body is read: key configured (503), key matches (401), mode (503).
   - `DATA_SOURCE` (default `mock`; an unknown value runs as `mock`, and `GET /api/health` then shows it as `requested_data_source`): `mock` simulator only (pushes refused), `hybrid` simulator plus device, `device` device only. Pushed points carry provenance `LIVE_HW`. In `hybrid` a push using a simulated truck id is rejected per point (`truck_id <id> is a simulated truck; use another id`).
   - Render free plan sleeps when idle: the first request after sleep can take 30 to 60 s, so the device needs a long timeout and retries (or use the Starter plan).
3. BFF -> React (BFF default port 4000, `PORT`):
   - REST: `GET /api/trucks` (`{ server_time, freshness, health_rules, trip_rules, driver_rules, trucks[] }`; `trip_rules` is `rules.trips`: `{ start_speed_kmh, start_hold_s, stop_hold_s, no_data_end_s, stop_speed_kmh, assignment_early_s }`; `driver_rules` is `rules.driver`: `{ max_gap_s, harsh_accel_kmh_s, harsh_brake_kmh_s, overspeed_kmh, idle_min_s, start_score, points: { harsh_brake, harsh_accel, overspeed_per_min, idle_per_min } }`), `GET /api/trucks/:truck_id/history?from=&to=&limit=` (`{ truck_id, points[] }`, raw telemetry objects ascending; `from`/`to` are epoch ms or contract timestamps; `limit` (positive integer, max 5000) keeps the newest N points; other values are ignored; 404 for a truck with no stored points), `GET /api/health` (`{ ok, data_source, requested_data_source, uptime_s, trucks, pipeline, server_time }`), `GET /api/alerts?status=ACTIVE|ACKNOWLEDGED|RESOLVED|open&truck_id=&kind=health|sos|geofence` (`{ alerts[] }`, newest first), `GET /api/alerts/events?limit=` (`{ events[] }`, newest first), `PATCH /api/alerts/:id` with `{ status: "ACKNOWLEDGED"|"RESOLVED", note?, by? }` (returns `{ alert, event }`), `POST /api/trucks/:truck_id/sos` with `{ note?, by? }` (manual SOS; returns `{ alert, event }`; 404 unknown truck, 409 if the truck already has an open SOS of any trigger), `PATCH /api/sos/:id` (same body and response as `PATCH /api/alerts/:id`; 404 if the id is not an SOS), fleet manager data: `GET /api/registry` (`{ trucks[], drivers[], service_types[], storage: { kind, persistent } }`; registry `truck_id`s are kept exactly as entered and matched to telemetry case-sensitively), `POST /api/registry/trucks`, `PUT /api/registry/trucks/:truck_id`, `DELETE /api/registry/trucks/:truck_id`, `POST /api/registry/drivers`, `PUT /api/registry/drivers/:driver_id`, `DELETE /api/registry/drivers/:driver_id` (body `{ name (required, up to 60), phone? (20), licence_no? (30), truck_id? }`; `truck_id` is trimmed and must be a registry truck (else 400); it puts the driver on that truck in place of its current driver and off any other truck, `""` or null takes them off their truck, omitted leaves it as is; PUT keeps fields left out; DELETE leaves their truck without a driver, and past trips and events keep the name; POST 201 `{ driver }`, PUT 200 `{ driver }`, DELETE 200 `{ ok: true }`; a driver is `{ driver_id ("D-" + 8 hex chars for manager drivers), name, phone, licence_no, source: seed|manager, created_at, truck_id }` where `truck_id` is the registry truck the driver is on now, or null, in responses and in `GET /api/registry` `drivers[]`; every successful registry, service record, trip assignment or refuel POST/PUT/DELETE broadcasts `registry:update`), `GET /api/service-records?truck_id=`, `POST /api/service-records`, `DELETE /api/service-records/:id` (validation errors 400, conflicts 409, unknown ids 404), trips: `GET /api/trips?status=active|completed&truck_id=&limit=` (`{ trips[] }`, every active trip plus the kept completed ones, newest first by `start_ms`; `limit` caps the combined list (active and completed together), positive integer, default 200, max 1000, other values ignored; `truck_id` exact match; 400 on a non-empty status other than active/completed), `GET /api/trips/:id` (`{ trip }` where `trip` is the trip object without `has_path` plus `trip.path: { fields: ["t_ms","latitude","longitude","speed","rpm","engine_load","coolant_temp"], rows: [[...]] } | null`, rows ascending, a value the point lacked is null; `path` is always present for an active trip and null once a completed trip is no longer among the newest 100 completed paths kept; 404 unknown id, including completed trips dropped after the newest 500). A trip is `{ id ("T" + sequence number, e.g. "T12"), truck_id, driver_id, driver_name, provenance, from_zone, status: active|completed, start_at, start_ms, from_first_reading, end_at, end_ms, end_reason: stopped|no_data|null, last_at, duration_s, distance_km, max_speed, avg_speed, points, start_position, end_position, to_zone, alerts[{ id, kind, name, level, opened_at }], driving: { score, rated, events, deductions[{ type, count, minutes, points }] }, has_path }` (times are telemetry times; `end_at`/`end_ms`/`end_reason` are null while active; `duration_s` is whole seconds up to `end_ms` (active: up to `last_at`); `distance_km` rounded to 0.01 km, `max_speed`/`avg_speed` km/h rounded to 0.1; `avg_speed` is the mean of the readings with a numeric `speed`, stops included; `points` = path rows; `start_position`/`end_position` are `{ latitude, longitude }` of the first reading (null without a fix) and of the last fix; `from_zone`/`to_zone` are the name of the first zone (any zone, regardless of `truck_ids`) containing the start/end position, else null, and `to_zone` is null while active; `driver_id` (null without a driver) and `driver_name` are the truck's driver when the trip started; `driver_name` is the truck's `driver_name` (same value as the derived truck object, so it can be "No driver assigned" or "Not in fleet list", not null); `alerts` are the truck's alerts of any kind and status with `opened_at` between `start_at` and `end_at` (no upper bound while active), compared as timestamp strings, in the order they were raised; a manual SOS `opened_at` is BFF clock time, all others telemetry time; `from_first_reading` means the truck was already moving when its history began, so the real start is earlier; `driving` is the RULE-BASED driving score from the driver events (below) attributed to this trip (their `trip_id` is this trip's `id`; the trip keeps them, independent of the 2000-event buffer, so points lost only grow while the trip is kept): `score` = `start_score` minus the deductions' `points`, floor 0, or null with `rated: false` when the trip's readings average more than `max_gap_s` apart; `events` counts the attributed events; `deductions` is `[{ type, count, seconds, minutes, points }]`, one entry per event type that occurred, in the order harsh_brake, harsh_accel, overspeed, idling: for harsh events `points` is the sum of the events' `points` and `seconds`/`minutes` are null; for overspeed and idling `seconds` is the summed `duration_s` of that type's events (ongoing ones up to their latest reading), `minutes` = chargedMinutes(`seconds`) = whole minutes, at least 1 when `seconds` > 0, and `points` = `minutes` times `points.overspeed_per_min` / `points.idle_per_min` (charged on the trip's total time, not per event); `has_path` is true for active trips; trips live in memory and ids restart with the server). Trip assignments (fleet manager plans, stored with the registry): `GET /api/trip-assignments?truck_id=` (`{ assignments[] }`, soonest `planned_start` first, then by `created_at`), `POST /api/trip-assignments` with `{ truck_id, driver_id?, from_place, to_place, cargo?, planned_start: "YYYY-MM-DDTHH:MM", notes?, by? }` (`truck_id` is trimmed and must be in the registry; text fields are trimmed and an empty optional one is stored as null; `driver_id` omitted or null means the truck's current driver, `""` means no driver; `from_place`/`to_place` required, up to 60 chars; `cargo` up to 100, `notes` up to 300, `by` up to 60; `planned_start` may carry `:SS`, which is dropped, and is stored as a contract timestamp with seconds `00`, within 365 days of now either way; 400 on any invalid field including an unknown truck or driver; 201 `{ assignment }`), `DELETE /api/trip-assignments/:id` (200 `{ ok: true }`, 404 unknown id); an assignment is `{ id ("P-" + 8 hex chars), truck_id, driver_id, from_place, to_place, cargo, planned_start, notes, by, created_at, driver_name }` (`driver_name` is looked up on read, null without a driver); each successful POST/DELETE broadcasts `registry:update`. The dashboard links an assignment to the truck's first detected trip starting no earlier than `trip_rules.assignment_early_s` before the planned start (each trip used once, earliest plans first). Driver behaviour: `GET /api/driver-events?truck_id=&driver_id=&limit=` (`{ events[] }`, newest first by when each event was first reported (id order, not `start_ms`: a harsh event is reported when it ends, so it can follow a later-starting overspeed); `truck_id` and `driver_id` exact match; `limit` positive integer, default 500, max 2000, other values ignored; the 2000 most recently reported are kept in memory and reset with the server); an event is `{ id ("E" + sequence number), truck_id, trip_id, driver_id, driver_name, source: "RULE_BASED", type: harsh_brake|harsh_accel|overspeed|idling, start_at, start_ms, end_at, end_ms, duration_s, ongoing, peak, speed_from, speed_to, latitude, longitude, points }` (telemetry times; `trip_id` is the trip the event is attributed to, null until attributed: each time an event is recorded or changes, it joins the truck's running trip if its `end_ms` is at or after that trip's `start_ms`, else the truck's latest completed trip if they overlap in time (`start_ms` <= trip `end_ms` and `end_ms` >= trip `start_ms`), else it waits (newest 50 per truck); when the truck's next trip starts it claims the waiting events with `end_ms` at or after its `start_ms` (the rest are never attributed) and each claimed event is re-sent as `driver:event`; once attributed an event stays with its trip; `driver_id`/`driver_name` are the truck's registry driver when the event is first reported (for harsh events that is the reading that ends them, or the sweep that closes them) and become the trip's `driver_id`/`driver_name` once attributed, with `driver_name` the same value as the derived truck object's, so "No driver assigned" or "Not in fleet list" rather than null; the `driver_id` filter matches the current value; judged only between consecutive readings at most `max_gap_s` apart, both with a numeric `speed`: harsh events are one or more consecutive pairs whose speed change per second is above `harsh_accel_kmh_s` or below minus `harsh_brake_kmh_s`, from the reading before the first pair to the last reading of the last pair, `peak` = strongest rate as a positive number of km/h per second (for braking too); overspeed runs from the first reading above `overspeed_kmh` to the first reading at or under it, `peak` = highest speed, and is reported only once it spans two readings (a single reading above the limit followed by a gap is dropped); idling runs from the first reading with `speed` 0 and `rpm` > 0 to the first other reading and counts once longer than `idle_min_s`, `peak` null; a gap over `max_gap_s`, a reading without speed, or `rules.trips.no_data_end_s` (300 s) without an accepted reading (BFF receive time, checked by the 2 s sweep; the next reading then starts fresh, not paired with the last) ends an open event at its last reading; readings not newer than the last accepted one are ignored, except one more than `rules.trips.no_data_end_s` (300 s) behind it, which is a device clock reset and also ends open events at their last reading; `latitude`/`longitude` of the first reading, null without a fix; `ongoing` true while overspeed or idling continues; `points` = `points.harsh_brake` / `points.harsh_accel` for harsh events, null for overspeed and idling (they are charged per trip on their total time, see trip `driving`)). Fuel (`rules.fuel`, in memory, resets with the server): `GET /api/fuel` (`{ rules, trucks[], events[] }`; `rules` is `rules.fuel`: `{ base_lph, load_factor, rpm_ref, theft_drop_pct, refuel_rise_pct, anomaly_window_s, sample_every_s }`, not editable and not in `/api/rules`; `trucks` = `[{ truck_id, ...fuel summary }]` for every truck with at least one accepted reading, sorted by `truck_id`; `events` = newest 200 fuel events, newest first by when first recorded (id order); the newest 500 are kept), `GET /api/fuel/:truck_id/history` (`{ truck_id, fields: ["t_ms","level_pct","source","used_l"], rows: [[...]] }`, oldest first, one row at most every `sample_every_s` (30 s) of telemetry time, newest 480 kept (4 h), `source` per row `sensor|estimate`, `used_l` the fuel summary's cumulative ESTIMATED litres since `since` as of that row (rounded to 0.1); after a device clock reset the rows are cleared and start again from the reset point, so `t_ms` never runs backwards; 404 for a truck with no accepted reading); the fuel summary (also the derived truck `fuel` field) is `{ source: sensor|estimate, level_pct, level_l, capacity_l, used_l, idle_l, distance_km, km_per_l, since, updated_at }` (`source` is `sensor` only when the truck's newest accepted reading carried a valid `fuel_level`; `level_pct`/`level_l`/`used_l`/`idle_l` rounded to 0.1, `distance_km` to 0.01, `km_per_l` to 0.01 and null until `used_l` >= 1 L; `capacity_l` is the registry `tank_capacity_l`; `used_l`, `idle_l`, `distance_km`, `km_per_l` are always ESTIMATED from the burn model, counted since `since` (telemetry time of the first reading tracked since server start or warm start); `updated_at` is the newest accepted reading's `timestamp`); level: a `fuel_level` reading (numeric, 0 to 100) sets the level as is; without one the level is ESTIMATED, starting from a full tank at the first reading and burning `L/h = base_lph + load_factor x engine_load x (rpm / rpm_ref)` (2 + 0.25 x load x rpm/2000) while `rpm` > 0, from the previous reading's values over the time to this one, only between readings at most `rules.freshness.stale_after_s` (15 s) apart (a longer gap burns nothing and adds no distance); `idle_l` is burn while the previous reading's `speed` is exactly 0; distance is the haversine sum between consecutive fixes within that gap; a truck whose sensor stops reporting continues estimating from its last measured level; readings not newer than the last accepted one are ignored, except one more than `rules.trips.no_data_end_s` (300 s) behind it (device clock reset), which is accepted without integrating the gap, closes any open fuel event at its last reading and restarts anomaly judging (window, pending glitch check) and the sensor state from that point (the level and consumption totals carry on). A fuel event is `{ id ("F" + sequence number), truck_id, driver_id, driver_name, source: "RULE_BASED", type: theft|refuel, start_at, start_ms, end_at, end_ms, ongoing, from_pct, to_pct, litres, latitude, longitude }` (telemetry times; opened only by valid `fuel_level` readings, an estimate never raises one; each such reading joins a window of the last `anomaly_window_s` (60 s) of sensor readings, and both kinds are judged on the run of consecutive `speed` 0 readings at the end of that window, ending with the current one (a moving current reading judges nothing): `theft` when the level is more than `theft_drop_pct` (5) below the run's highest level, else `refuel` when it is more than `refuel_rise_pct` (5) above the run's lowest level; it starts at that highest/lowest reading; a reading past a limit opens nothing by itself: the next sensor reading must be past the same kind's limit too, and then the event opens on that second reading; if the next sensor reading does not agree, the first is treated as a glitch, dropped from the window, and the second is judged without it (a reading without a valid `fuel_level` does not enter the window; it cancels the pending check and the first reading stays in the window); a reading of the kind already open does not open another, one of the opposite kind (confirmed the same way) closes the open event and opens the new one; after an event opens the window restarts from the opening reading and later sensor readings keep entering it; while open, `to_pct`/`end_at`/`end_ms` follow each further drop (truck still stopped) or rise; on every accepted reading, with or without `fuel_level`, an open event closes if it is a theft and `speed` is a number above 0, or if the reading is more than `anomaly_window_s` after the event's last further change (`end_at` stays at that last change); it also closes on a device clock reset (see above) or when the truck has sent nothing for `rules.trips.no_data_end_s` (300 s, BFF receive time, 2 s sweep); `litres` = abs(`from_pct` - `to_pct`) / 100 x the tank capacity, rounded to 0.1; `latitude`/`longitude` of the start reading, null without a fix; `driver_id`/`driver_name` are the truck's registry driver when the event is first recorded, `driver_name` the same value as the derived truck object's). Manager refuels (stored with the registry): `GET /api/refuels?truck_id=` (`{ refuels[] }`, newest `at` first, then newest `created_at`), `POST /api/refuels` with `{ truck_id, litres, cost_inr?, at?, notes?, by? }` (`truck_id` trimmed and must be in the registry; `litres` required, 1 to the truck's `tank_capacity_l`; `cost_inr` 0 to 1000000, empty or omitted stored as null; numeric strings accepted; `at` "YYYY-MM-DDTHH:MM" (`:SS` accepted and dropped), stored as a contract timestamp with seconds `00`, within 365 days of now and at most 60 s in the future, omitted or `""` means the current minute; `notes` up to 300, `by` up to 60; 400 on any invalid field; 201 `{ refuel, applied_to_estimate }`; `applied_to_estimate` is true when the truck has fuel tracking state, its newest accepted reading carried no valid `fuel_level` (`fuel.source` is `estimate`), and `at` is not earlier than its first tracked reading: the estimate then rises by `litres`, capped at the tank, and `fuel:level` is sent; it is false otherwise and nothing changes or is sent (a measured level is left alone; a refuel before tracking began is already in the full tank the estimate started from; also false when the truck has sent no reading since server start); the refuel is saved either way), `DELETE /api/refuels/:id` (200 `{ ok: true }`, 404 unknown id; does not lower the level again); a refuel is `{ id ("R-" + 8 hex chars), truck_id, litres, cost_inr, at, notes, by, source: "manager", created_at }`; each successful POST/DELETE broadcasts `registry:update`. Analytics (in memory, resets with the server): `GET /api/analytics?range=15m|1h|session` (default `1h`, 400 `{ error }` for any other value) returns `{ range, from_ms, to_ms, generated_at, alerts: { rules[], trucks[{ truck_id, total, by_rule: { name: count } }], total }, risk: { every_s, window_s, series[{ truck_id, points: [[t_ms, score]] }] } | null, trips[{ id, truck_id, driver_id, driver_name, start_at, end_ms, distance_km, duration_s, score }], drivers[{ driver_id, driver_name, trips, score }], fuel[{ truck_id, used_l, level_source }], costs[{ truck_id, service_inr, refuel_inr, refuel_l, entries }] }` (the range ends now on the BFF clock: `to_ms` = BFF epoch ms at computation; for `15m`/`1h` the lower bound and `from_ms` are `to_ms` minus 900 / 3600 s; `session` has no lower bound (everything still held: completed trips, risk samples, alerts, the ring buffer) and its `from_ms` reports the earliest held item: the oldest ring buffer reading, oldest risk sample or oldest completed trip `start_ms` of any truck (`to_ms` if none); items are matched on their own times (telemetry time for readings, risk samples, trips and telemetry alerts; BFF time for a manual SOS and manager refuels), and "in range" means lower bound <= t <= `to_ms` + `rules.ingest.max_future_s` (300 s), so items stamped slightly ahead of the BFF clock still count; `generated_at` = `to_ms`; each range's body is cached 10 s by BFF clock and served unchanged (same `generated_at`/`to_ms`) meanwhile; with no truck in the store at all: `from_ms`/`to_ms` null, `risk` null, `alerts` `{ rules: [], trucks: [], total: 0 }`, every list empty; lists are otherwise empty when nothing qualifies, never sample data. `alerts`: every alert of any kind and status whose `opened_at` is in range, counted per truck by alert `name`; `rules` = the names ordered by total count desc, then name; `trucks` sorted by `truck_id`, only trucks with at least one; `total` = sum. `risk`: RULE_BASED rule risk score (0 to 100, `rules.risk`/`rules.health`) per truck, sampled once per `every_s` (30) s of telemetry per truck over the `window_s` (`rules.risk.window_s`) seconds of stored readings up to the sample; the newest 480 samples per truck kept (4 h); a reading older than the truck's last sample is skipped, unless it is more than `rules.trips.no_data_end_s` (300 s) behind it (device clock reset), which clears the truck's samples and starts again from that reading; `series` sorted by `truck_id`, only trucks with a sample in range, `points` oldest first, thinned on one time grid shared by all trucks: step = 30 s x ceil(most in-range samples of any truck / 120) (at least 30 s), keeping each truck's first sample in every floor(`t_ms` / step) slot; `every_s` reports that step in seconds (30 when not thinned), and a client lines trucks up by bucketing on floor(`t_ms` / (`every_s` x 1000)). `trips`: completed trips (of the newest 500 kept) whose `end_ms` is in range, oldest `start_ms` first; `score` = trip `driving.score` (null when not rated). `drivers`: from those `trips` with a non-null `driver_id` and `score`, grouped by `driver_id`; `trips` = count, `score` = rounded mean, `driver_name` from the earliest such trip; sorted by `score` desc, then `driver_name`. `fuel`: ESTIMATED litres burnt in range per truck with an accepted reading: current summary `used_l` minus a base, floor 0, rounded to 0.1; the base is the cumulative `used_l` at the lower bound, interpolated linearly in `t_ms` between the fuel history rows either side of it (the last row's `used_l` when all rows are at or before it); with no row at or before it the base is 0 if tracking began (`since`) inside the range (always so for `session`), else the first kept row's `used_l` (rows restarted after a device clock reset); `level_source` = the truck's current `fuel.source`; trucks with 0 left out; order of `GET /api/fuel` `trucks`. `costs`: MANUAL fleet manager entries per truck, sorted by `truck_id`: service records with a non-null `cost_inr` whose `date` day (00:00 to 24:00 local) overlaps lower bound..`to_ms` (no future allowance) add to `service_inr`; refuels whose `at` is in range add `cost_inr` (null as 0) to `refuel_inr` and `litres` to `refuel_l`; `entries` counts both; trucks with no entry left out). geofences: `GET /api/geofences?truck_id=` (`{ zones[], visits[] }`; `zones` is always every zone; `visits` = newest 100 confirmed entries/exits, newest first, filtered by `truck_id` when given), `POST /api/geofences` (201, `{ zone }`), `PUT /api/geofences/:id` (200, `{ zone }`; fields left out keep their value), `DELETE /api/geofences/:id` (200, `{ ok: true }`) (zone `{ id ("Z-" + 8 hex chars for manager zones), name (required, up to 60 chars, unique ignoring case), center_lat (-90 to 90), center_lng (-180 to 180), radius_m (50 to 50000), type: allowed|restricted, alert: bool (default true), truck_ids: [] (up to 50 valid truck IDs, stored deduplicated and sorted; empty = every truck; limits alerts only, see Rules), source: seed|manager, updated_at (contract timestamp) }`; numeric strings are accepted for the numbers; a centre of exactly 0, 0 is rejected; 400 invalid, 409 duplicate name, 404 unknown id; every successful POST/PUT/DELETE broadcasts `geofences:update`, then any zone alerts it closes as `alert:update`), alert thresholds: `GET /api/rules` (`{ demo_tuned, health[{ ...rule, default_threshold, limits: [min, max] | null }], freshness, alerts, sos, risk, geofence, trips, driver }`; There is no FastAPI hop: the device posts straight to the BFF.

## Telemetry object (field names, types and casing are fixed)
| field | type | unit / format |
|---|---|---|
| `truck_id` | string | e.g. `"TN01"` |
| `timestamp` | string | ISO 8601, no TZ suffix, treated as local time, e.g. `"2026-09-10T10:00:00"` |
| `latitude` | float | WGS84 degrees |
| `longitude` | float | WGS84 degrees |
| `coolant_temp` | number | °C |
| `oil_temp` | number | °C |
| `battery_voltage` | number | V |
| `rpm` | int | rev/min |
| `engine_load` | number | 0 to 100 % |
| `speed` | number | km/h |

Optional (auto-detected when present, passed through as stored and listed in `optional_fields`). Device pushes are normalized before storage (see Hops 2): numeric strings become numbers, `sos` becomes a boolean, unreadable optional values are dropped (so they never reach the store or `optional_fields`). Simulated points already carry these types. `sos`, `fuel_level` and `maintenance_risk_score` are implemented:
| field | type | meaning |
|---|---|---|
| `fuel_level` | number | tank level, 0 to 100 % of the registry `tank_capacity_l`. A numeric value in range replaces the fuel estimate (truck `fuel.source: "sensor"`) and is the only input to theft/refuel anomaly detection (see `GET /api/fuel`); an out-of-range number is ignored for fuel (the level keeps being estimated) but still passed through; a pushed value that is neither a number nor a numeric string is dropped at ingest. Simulator: only TN01 sends it (`FUEL_SENSOR_TRUCKS`), 1 decimal |
| `sos` | bool | hardware panic button; `true` raises an SOS (one open SOS per truck; a person closes it) |
| `maintenance_risk_score` | number | 0 to 100, ML model output. Read from the truck's newest point only: a stored number from 0 to 100 inclusive becomes the truck's `ml_risk` (`source: "device"`, rounded) in place of the fleet server's own model (a pushed numeric string is converted to a number at ingest, so it counts); an out-of-range number is ignored for `ml_risk` but still passed through; a pushed value that is neither a number nor a numeric string is dropped at ingest |

`sos` semantics (as implemented in `dashboard/server/services/alerts.js` `evaluateSos`):
- Only a stored boolean `true` raises an SOS (strict `=== true`). A device push is normalized first (Hops 2): `true`, `1`, `"1"` and `"true"` are stored as `true` and do raise an SOS; `false`, `0`, `"0"` and `"false"` are stored as `false`; any other value (including `null`) is dropped, so `sos` is then absent from the point and from `optional_fields`. `false` or omitting the field are equivalent.
- The flag is read from the truck's newest point only, once per ingest batch. Device pushes are fed one point per batch in time order, so every pushed point is evaluated. A `sos: true` point that is not the newest point for its truck in a batch, arrives older than the stored latest point, or repeats an already-seen `timestamp` is never evaluated.
- One open SOS per truck, shared by all triggers (manual, hardware, collision). While any SOS is open for the truck, further `sos: true` points are ignored.
- The SOS stays open until a person resolves it. Only a change of `sos` to `true` raises one: a device that keeps sending `true` (latching button) raises a single SOS, and a new one only after it has sent a non-true value and then `true` again.
- A hardware SOS takes `opened_at` from the point's `timestamp` and its `latitude`/`longitude` from the same point.

## Rules
- Nominal rate 1 Hz per truck. Points are deduplicated by (`truck_id`, `timestamp`), comparing the exact `timestamp` string. Points with no `truck_id` or an unparseable `timestamp` are dropped. Points whose `timestamp` is more than 300 s ahead of the BFF clock are dropped (`rules.ingest.max_future_s`).
- Truck is `stale` after 15 s without an update, `offline` after 60 s (measured on BFF receive time).
- Drivers, the truck to driver mapping and tank capacity are fleet manager data in the registry (seeded from `dashboard/server/config/fleet.js`), not part of the telemetry.
- Geofencing uses `latitude`/`longitude` only. A point without a usable fix (non-numbers, out of range, or exactly 0, 0) neither enters nor leaves a zone. A crossing is confirmed after `rules.geofence.confirm_points` (2) consecutive points on the new side. Only points newer than the last one judged for that truck and zone count (late or repeated points are ignored for zones), and a pending crossing lapses if the next point comes more than `rules.freshness.stale_after_s` (15 s) later. Only the newest point per truck in a batch is judged. Device pushes are fed one point per batch, oldest first (Hops 2), so every point of a pushed backlog is judged, provided it is newer than the truck's stored latest point; backlog points older than a live point already received are not judged for zones. A truck's first confirmed side of a zone (after its first 2 fixes, or after a BFF restart) sets `zones_inside` but is not logged as a visit. Entries, exits and `zones_inside` are tracked for every zone and every truck; a zone's `truck_ids` and `alert` only decide which trucks it raises alerts for.
- Trips (`rules.trips`): a trip starts once `speed` has stayed above 5 km/h for 30 s (it begins at the first of those readings; readings more than 30 s apart do not add up to a start) and ends when `speed` has been at or below `stop_speed_kmh` (0, exactly 0 as the spec says) for more than 2 min (the end is the first such reading, and distance and stats stop there), or after 5 min without data (the end is the last reading, or the stop reading if a stop was already pending). "Without data" means any of: a gap of more than 300 s in telemetry time between accepted readings; more than 300 s since the BFF received the last reading the trip engine accepted (checked by the 2 s sweep); or 300 s of readings none of which has a numeric `speed`. A reading without a numeric `speed` breaks a pending start but not a pending stop. Points not newer than the last one accepted for the truck are ignored, except that a timestamp more than 300 s behind it is treated as a device clock reset: the trip ends and detection restarts from that point. Every point the store accepts is judged, in time order (live batches and warm-start history alike). Distance is the haversine sum between consecutive fixes, with no GPS-glitch filter. Trips live in memory and reset with the server.
- Fuel (`rules.fuel`): every point the store accepts is fed to the fuel tracker, in time order, after trips and driver events (live batches and warm-start history alike). Burn model and anomaly rules as under `GET /api/fuel`. Simulated sensor truck (TN01) starts at 100 %, burns with the same model on a fixed 300 L tank, and at a depot stop (waypoint `dwell_s` >= 120 s) below 25 % refills at 0.5 % per second up to 100 %, which raises a `refuel` event. Other simulated trucks send no `fuel_level`, so their level is ESTIMATED.
- Analytics risk samples: every point the store accepts is fed to the analytics risk sampler, in time order, after trips and driver events and before fuel (live batches and warm-start history alike). See `GET /api/analytics`.
- Warm start (simulator only, `WARM_START_S`, default 4800 s, clamped to 0..4800; 0 or a non-number turns it off): at boot the simulator replays that much past driving into the ring buffer, trip detection, driver event detection, analytics risk sampling and fuel tracking, so history, trips, driver events, trip scores, risk trends, fuel levels and fuel events exist right away. These points are labelled `SIM`, raise no alerts, log no zone visits and are not broadcast (no `trip:update`, `driver:event` or `fuel:event` either). Hardware data is never back-filled.
