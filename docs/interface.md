# Hardware <-> Software Interface

## Hops
1. ESP32-WROOM + EC200U (4G) + GPS + OBD-II -> FastAPI (HTTP over 4G). Owned by hardware teammate.
2. FastAPI -> dashboard BFF (PLANNED, not implemented yet): BFF polls `GET {FASTAPI_URL}/latest` every 1 s over HTTPS, 3 s timeout. Response assumed to be a JSON array of telemetry objects (shape not final; all mapping lives in `dashboard/server/services/source.js`). Today `DATA_SOURCE=fastapi|hybrid` logs a warning and falls back to the built-in simulator (`DATA_SOURCE=mock`, provenance `SIM`); `FASTAPI_URL` is not read by any code yet.
3. BFF -> React (BFF default port 4000, `PORT`):
   - REST: `GET /api/trucks` (`{ server_time, freshness, health_rules, trucks[] }`), `GET /api/trucks/:truck_id/history?from=&to=&limit=` (`{ truck_id, points[] }`, raw telemetry objects ascending; `from`/`to` are epoch ms or contract timestamps; `limit` (positive integer, max 5000) keeps the newest N points; other values are ignored), `GET /api/health` (`{ ok, data_source, requested_data_source, uptime_s, trucks, pipeline, server_time }`), `GET /api/alerts?status=ACTIVE|ACKNOWLEDGED|RESOLVED|open&truck_id=&kind=health|sos|geofence` (`{ alerts[] }`, newest first), `GET /api/alerts/events?limit=` (`{ events[] }`, newest first), `PATCH /api/alerts/:id` with `{ status: "ACKNOWLEDGED"|"RESOLVED", note?, by? }` (returns `{ alert, event }`), `POST /api/trucks/:truck_id/sos` with `{ note?, by? }` (manual SOS; returns `{ alert, event }`; 404 unknown truck, 409 if the truck already has an open SOS of any trigger), `PATCH /api/sos/:id` (same body and response as `PATCH /api/alerts/:id`; 404 if the id is not an SOS), fleet manager data: `GET /api/registry` (`{ trucks[], drivers[], service_types[], storage: { kind, persistent } }`; registry `truck_id`s are kept exactly as entered and matched to telemetry case-sensitively), `POST /api/registry/trucks`, `PUT /api/registry/trucks/:truck_id`, `DELETE /api/registry/trucks/:truck_id`, `POST /api/registry/drivers`, `GET /api/service-records?truck_id=`, `POST /api/service-records`, `DELETE /api/service-records/:id` (validation errors 400, conflicts 409, unknown ids 404), geofences: `GET /api/geofences?truck_id=` (`{ zones[], visits[] }`; `zones` is always every zone; `visits` = newest 100 confirmed entries/exits, newest first, filtered by `truck_id` when given), `POST /api/geofences` (201, `{ zone }`), `PUT /api/geofences/:id` (200, `{ zone }`; fields left out keep their value), `DELETE /api/geofences/:id` (200, `{ ok: true }`) (zone `{ id ("Z-" + 8 hex chars for manager zones), name (required, up to 60 chars, unique ignoring case), center_lat (-90 to 90), center_lng (-180 to 180), radius_m (50 to 50000), type: allowed|restricted, alert: bool (default true), truck_ids: [] (up to 50 valid truck IDs, stored deduplicated and sorted; empty = every truck; limits alerts only, see Rules), source: seed|manager, updated_at (contract timestamp) }`; numeric strings are accepted for the numbers; a centre of exactly 0, 0 is rejected; 400 invalid, 409 duplicate name, 404 unknown id; every successful POST/PUT/DELETE broadcasts `geofences:update`, then any zone alerts it closes as `alert:update`), alert thresholds: `GET /api/rules` (`{ demo_tuned, health[{ ...rule, default_threshold, limits: [min, max] | null }], freshness, alerts, sos, risk, geofence }`; `limits` is null only for a field with no `rules.threshold_limits` entry), `PUT /api/rules` with `{ thresholds: { rule_id: number } }` (rules left out keep their value; 400 when `thresholds` is missing or not an object, names an unknown rule id, a value is not a finite number inside `rules.threshold_limits`, a warning would not fire before its critical rule, or a "below" limit is not under an "above" limit on the same field; returns the same shape as GET plus `changed_fields` (fields whose thresholds changed) and broadcasts `rules:update`; open health alerts on a changed field close with `resolution: rule_changed` (event type `closed`, sent as `alert:update`) and the next point judges the field against the new thresholds; `GET /api/trucks` `health_rules` reflects the edited values), `GET /api/demo/scenarios` (`{ enabled, available[{ id, label, description, default_truck, duration_s, needs: "restricted_zone" | null }], running[] }`; `enabled` is false when `DEMO_ENABLED=false` or the simulator is not running; `running[]` items have the same shape as `run` below), `POST /api/demo/scenario` with `{ scenario, truck_id? }` (returns `{ run: { id, scenario, truck_id, target, started_ms, ends_ms }, running[] }`, where `run.id` is the scenario key, `run.scenario` its label and `target` the zone name for `geofence_breach` (the nearest restricted zone covering the truck, zones with alerts on first), null for every other scenario; 403 when `DEMO_ENABLED=false`, 409 without the simulator or, for `geofence_breach`, when no restricted zone covers the truck, 400 unknown scenario or non-simulated truck). `pipeline` is `{ mode, hops[{ id: device|sim|bff, label, status: ok|degraded|down, detail }], latency_ms, server_time }` (`latency_ms` is null unless live hardware trucks are reporting).
   - Socket.IO: `truck:update` (one derived truck object per truck that received new points in a batch, built from that truck's newest point, plus `server_time`). `alert:new` / `alert:update` (`{ alert, event }`; `event` is null for condition-only updates; `alert.version` increases on every change). `registry:update` (no payload; reload `GET /api/registry`), `geofences:update` (no payload; reload `GET /api/geofences`), `zone:visit` (one confirmed entry or exit: `{ id, truck_id, driver_name, zone_id, zone_name, zone_type, type: entered|left, at, at_ms }`, dated at the first point on the new side, so `at`/`at_ms` are telemetry time, not BFF receive time; sent before the `truck:update` of the confirming point), `rules:update` (no payload; reload `GET /api/rules`), `pipeline:status` (same shape as `/api/health` `pipeline`, every 2 s). Alerts have `kind: "health" | "sos" | "geofence"`; geofence alerts carry `source: "RULE_BASED"`, `driver_name`, `zone_id`, `zone_name`, `zone_type`, `name` ("Inside restricted zone" / "Outside allowed zone"), `level` (`critical` restricted, `warning` allowed), `field: null`, `unit: "m"`, `value` (metres from the zone centre when opened), `last_value` (latest) and `peak_value` (worst so far), `op` (`<` restricted, `>` allowed), `threshold` (radius, m), `latitude`/`longitude`/`location_at` of the point where the breach was confirmed, `condition: firing | unknown (no GPS fix) | no_data | cleared`; geofence events add `zone_id`, `zone_name`, `zone_type`, `value`. A geofence alert resolved by hand stays quiet until the truck is back on the right side. Geofence alerts close on their own (`resolution: cleared`) once the truck is confirmed back on the right side, or with `zone_removed` / `zone_changed` (event type `closed`) when the zone is deleted, its alerts are turned off, it changes type, or it no longer covers the truck; SOS carry `trigger: manual | hardware | collision` and the last known `latitude`/`longitude`/`location_at`.
   - Derived truck objects carry every contract field verbatim and add only: `status`, `health`, `findings`, `freshness`, `provenance`, `driver_id`, `driver_name`, `received_at` (epoch ms), `last_seen_s`, `optional_fields` (names of optional fields present), `registration`, `model`, `tank_capacity_l`, `in_registry` (from the fleet registry), `zones_inside` (`[{ zone_id, zone_name, zone_type, since }]`, zones the truck is confirmed inside, as of this point), `rule_risk_score` (0 to 100) and `risk_breakdown` (`[{ field, rule_name, op, threshold, unit, weight, exposure, intensity, breach_s, worst_value, points }]`, last `rules.risk.window_s` seconds).

The ESP32 never talks to the BFF directly. `FASTAPI_URL` must be a public HTTPS URL.

## Telemetry object (field names, types and casing are fixed)
| field | type | unit / format |
|---|---|---|
| `truck_id` | string | e.g. `"TN01"` |
| `timestamp` | string | ISO 8601, no TZ suffix, treated as local time, e.g. `"2026-09-10T10:00:00"` |
| `latitude` | float | WGS84 degrees |
| `longitude` | float | WGS84 degrees |
| `coolant_temp` | number | °C |
| `oil_temp` | number | °C |
| `battery_voltage` | number | V |
| `rpm` | int | rev/min |
| `engine_load` | number | 0 to 100 % |
| `speed` | number | km/h |

Optional (auto-detected when present, passed through verbatim and listed in `optional_fields`). `sos` is implemented; `fuel_level` and `maintenance_risk_score` behaviour is PLANNED:
| field | type | meaning |
|---|---|---|
| `fuel_level` | number | 0 to 100 %, replaces the fuel estimate |
| `sos` | bool | hardware panic button; `true` raises an SOS (one open SOS per truck; a person closes it) |
| `maintenance_risk_score` | number | 0 to 100, ML model output |

`sos` semantics (as implemented in `dashboard/server/services/alerts.js` `evaluateSos`):
- Only the JSON boolean `true` raises an SOS (strict `=== true`). `"true"`, `1`, `"1"` and `null` do not raise anything and log nothing; they are still passed through verbatim and `sos` still appears in `optional_fields`. `false` or omitting the field are equivalent.
- The flag is read from the truck's newest point only, once per ingest batch. A `sos: true` point that is not the newest point for its truck in a batch, arrives older than the stored latest point, or repeats an already-seen `timestamp` is never evaluated.
- One open SOS per truck, shared by all triggers (manual, hardware, collision). While any SOS is open for the truck, further `sos: true` points are ignored.
- The SOS stays open until a person resolves it. Only a change of `sos` to `true` raises one: a device that keeps sending `true` (latching button) raises a single SOS, and a new one only after it has sent a non-true value and then `true` again.
- A hardware SOS takes `opened_at` from the point's `timestamp` and its `latitude`/`longitude` from the same point.

## Rules
- Nominal rate 1 Hz per truck. Points are deduplicated by (`truck_id`, `timestamp`), comparing the exact `timestamp` string. Points with no `truck_id` or an unparseable `timestamp` are dropped. Points whose `timestamp` is more than 300 s ahead of the BFF clock are dropped (`rules.ingest.max_future_s`).
- Truck is `stale` after 15 s without an update, `offline` after 60 s (measured on BFF receive time).
- Driver mapping and tank capacity are BFF config (`dashboard/server/config/fleet.js`), not part of the telemetry.
- Geofencing uses `latitude`/`longitude` only. A point without a usable fix (non-numbers, out of range, or exactly 0, 0) neither enters nor leaves a zone. A crossing is confirmed after `rules.geofence.confirm_points` (2) consecutive points on the new side. Only points newer than the last one judged for that truck and zone count (late or repeated points are ignored for zones), and a pending crossing lapses if the next point comes more than `rules.freshness.stale_after_s` (15 s) later. Only the newest point per truck in a batch is judged, so a backlog uploaded after an outage can hide a crossing (see plan step 12). A truck's first confirmed side of a zone (after its first 2 fixes, or after a BFF restart) sets `zones_inside` but is not logged as a visit. Entries, exits and `zones_inside` are tracked for every zone and every truck; a zone's `truck_ids` and `alert` only decide which trucks it raises alerts for.
