# Assumptions

Choices made where the spec left room. Each is isolated behind config so it can change without touching the rest.

| # | Assumption | Where |
|---|---|---|
| 1 | Freshness (stale > 15 s, offline > 60 s) is measured on BFF receive time, not the telemetry `timestamp`, so device clock drift cannot make a live truck look stale. | `server/services/fleet.js`, `server/config/rules.js` |
| 2 | Contract timestamps have no TZ suffix; the BFF interprets them in `TZ` (default `Asia/Kolkata`). | `server/.env.example` |
| 3 | Driver names and the truck to driver mapping are placeholders until the team provides real ones. | `server/config/fleet.js` |
| 4 | Each health rule reports only its highest level per field (a coolant reading of 112 shows "Coolant critical", not also "Coolant high"). | `server/engine/health.js` |
| 5 | The sustained engine-load rule needs data covering the full 60 s window with no gap over 5 s (`max_gap_s`); a dropout means it does not fire. | `server/engine/health.js` |
| 6 | Simulated routes are straight lines between real Chennai landmarks, not road-snapped. | `server/sim/routes.js` |
| 7 | Simulated trucks switch the engine off during long depot stops (>= 120 s) after 20 s of idling, so battery rules (engine running only) and trip end detection both get exercised. | `server/sim/simulator.js` |
| 8 | In local dev the client defaults to `http://localhost:4000` when `VITE_API_URL` is unset. Production builds require `VITE_API_URL` and show a setup message without it. | `client/src/config.js` |
| 9 | Until the FastAPI wiring step, `DATA_SOURCE=fastapi` or `hybrid` logs a warning and runs the simulator; `/api/health` reports both the requested and the effective source. | `server/services/source.js` |
| 10 | Requests with no `Origin` header (curl, container health checks) bypass the CORS allow-list; browsers always send one. | `server/services/cors.js` |
| 11 | Points stamped more than 300 s ahead of the BFF clock are dropped (`ingest.max_future_s`), so a device whose clock is not yet set cannot freeze its tile on a bogus future point. | `server/config/rules.js`, `server/services/store.js` |
| 12 | Battery rules fire only when the bad voltage holds for 10 s with the engine running (`sustain_s: 10`), so the 1 to 2 s dip while cranking is not an alert. Demo-tuned; to be confirmed with the hardware teammate. | `server/config/rules.js`, `server/engine/health.js` |
| 13 | "Held" means every reading in the window breaches; one reading back on the good side restarts the count. Readings missing the needed values are skipped (the gap limit still applies). "Engine running" is `rpm > 0` as specified, so an unusually long crank (over 10 s) could still raise a battery alert; a higher running-rpm cut-off needs a value from the hardware teammate. | `server/engine/health.js` |
| 14 | A GPS position of exactly 0,0 (or out of range) is treated as "no fix" and not drawn on the map or in trails. How the hardware reports "no fix" is to be confirmed with the hardware teammate. | `client/src/lib/position.js` |
| 15 | One alert per truck and field. It escalates warning to critical in place (an acknowledged alert becomes ACTIVE again), and closes on its own only after the raw value has been within every threshold for that field for 10 s (`alerts.clear_after_s`). Points where the field cannot be judged (engine off for battery rules, missing value) neither start nor extend that window, and a truck that stops reporting marks its alerts "no data" instead of letting them close. | `server/engine/alerts.js`, `server/config/rules.js` |
| 16 | An alert resolved by hand while its value is still out of limits stays quiet until the value has been within limits for the same 10 s; a later breach opens a new alert. | `server/services/alerts.js` |
| 17 | Acknowledge / resolve actions are not authenticated (hackathon scope). Browsers from other origins are blocked by CORS, but anyone who can call the API directly could act on alerts. | `server/routes/alerts.js` |
| 18 | SOS uses the alert lifecycle but never closes on its own; a person resolves it. At most one open SOS per truck: further triggers while one is open are ignored (manual trigger answers 409). | `server/services/alerts.js` |
| 19 | "Possible collision" is a heuristic (speed from >= 40 to <= 5 km/h within 3 s, `rules.sos.collision`), always labelled as such and badged RULE-BASED. | `server/engine/sos.js` |
| 20 | Demo scenarios only drive simulated trucks and are open to anyone who can reach the API; set `DEMO_ENABLED=false` to turn them off. | `server/sim/scenarios.js` |
| 21 | SOS sound is off by default (browsers block audio until the viewer interacts); the choice is remembered per browser. | `client/src/components/SOSBanner.jsx` |
| 22 | Pipeline latency (now minus newest timestamp) is shown only for LIVE HW trucks; simulated timestamps are generated by the server itself. | `server/services/pipeline.js` |
| 23 | Fleet manager data (trucks, drivers, service records) is saved through a storage adapter. Today it is JSON files in `DATA_DIR`; on Render's free plan that folder resets on restart or sleep, and the registry re-seeds the five demo trucks. A Postgres backend (Neon) selected by `DATABASE_URL` is planned. | `server/services/storage.js` |
| 24 | Rule-based maintenance risk (0 to 100) = for each field past its warning threshold in the last 10 min: weight x share of time past it x (0.5 + 0.5 x how far past, as a share of the way to critical). Weights sum to 100 and are demo-tuned (`rules.risk`). | `server/engine/risk.js` |
| 25 | A driver can be assigned to at most one truck. A truck's `truck_id` cannot be changed after it is created, because it must match what the device sends. | `server/services/registry.js` |
| 26 | Zones are circles. A restricted zone is breached while a covered truck is inside it, an allowed zone while a covered truck is outside it. Each zone has "alert on breach" (on or off) and "applies to" (all trucks, or listed trucks). Entries and exits are logged for every zone either way. The seeded depot and port are on normal routes, so they are seeded with alerts off; the restricted zone sits about 400 m clear of every simulated route. | `server/config/geofences.js` |
| 27 | Zone alerts follow the confirmed side, not the moment of crossing: a truck already in breach after a restart, or when alerts are switched on, raises one. Restricted breaches are critical, allowed breaches warnings. They clear on their own once the truck is confirmed back on the right side; resolved by hand mid-breach, they stay quiet until then. | `server/services/alerts.js` |
| 28 | The geofence breach scenario moves the simulated truck's reported position in a straight line to the zone centre over 25 s, parks it for 25 s, and returns it. The detour is faster than a real truck could drive; it is a demo input. The truck slows at 3 km/h per second so the stop is not read as a collision. | `server/sim/scenarios.js` |
| 29 | Alert thresholds edited in Settings apply at once to every engine (alerts, health colour, risk score) and are saved as overrides of the config defaults. Input bounds per field (`rules.threshold_limits`) are sanity limits for typing, not engineering limits. Open health alerts on an edited field close ("threshold changed") and the field is judged again against the new numbers, so an alert never shows a level or limit that no longer exists. Saving zones, thresholds or registry data writes the JSON file synchronously, pausing telemetry for a few milliseconds (up to about half a second if Windows briefly locks the file); acceptable for a single-instance demo, and the Postgres backend will remove it. | `server/services/ruleSettings.js` |
| 30 | Trip rules follow the spec (start after 30 s above 5 km/h, end after 2 min at 0 km/h or 5 min without data). Short stops (traffic, 30 to 40 s drops at waypoints) stay inside one trip; the simulator's depot stops (150 s) end one. Average speed is the mean of all readings in the trip, stops included. | `server/engine/trips.js` |
| 31 | The simulator replays 80 minutes of past driving at boot (warm start) so trips, replay and later charts have data right after a restart or a Render wake-up. It is simulated data, labelled SIM; it raises no alerts and is not sent live. Set `WARM_START_S=0` to turn it off. | `server/services/source.js` |
| 32 | Trips and their paths are kept in memory only (up to 500 trips, paths for the newest 100). They reset when the server restarts, like the ring buffer. | `server/services/trips.js` |
| 33 | A planned trip assignment is shown as done or on the road when the truck's first detected trip that starts no earlier than 30 minutes before the planned start exists; otherwise "not started yet" or "late". It does not check the route against from/to. | `client/src/lib/trips.js` |
| 34 | Driver events follow the spec (harsh acceleration above 8 km/h per second, harsh braking below -10, overspeed above 80 km/h, idling at 0 km/h with rpm > 0 for over 60 s, judged only between readings at most 3 s apart). Consecutive hard pairs are one event, not one per second. Overspeed and idling last until the first reading out of that state; their time is added up per trip and charged per whole minute, at least one, so a truck hovering around 80 km/h pays for its total time over the limit, not a minute per crossing. A trip whose readings average more than 3 s apart gets no score instead of a perfect one. Open events close after 5 min without data (receive time), so a store-and-forward backlog can still continue them. | `server/engine/driving.js`, `server/config/rules.js` |
| 35 | Each event belongs to one trip: the running trip if it ends after the trip began, else the last trip if they overlap (idling that starts at the stop), else it waits and a trip detected shortly after claims it (a harsh start from standstill happens before the 30 s start hold confirms the trip). Its driver is the trip's driver. A trip keeps its own events, so its score does not change when old events leave the 2000-event buffer. A driver's score is the average of their completed, rated trips kept in memory; score colours are 90 and up good, 70 to 89 warning, below 70 poor (display only). | `server/services/trips.js`, `client/src/lib/driving.js` |
| 36 | Adding or editing a driver with a truck puts them on it in place of its current driver (who is left without a truck). Removing a driver leaves their truck without one; past trips and events keep the name. | `server/services/registry.js` |
| 37 | The harsh braking scenario brakes TN04 from 50 to 20 km/h in two steps (16 then 14 km/h per second), recovers, and does it again; the steps stay harsh even if a reading arrives a little late, and it never drops near a stop, so it is not read as a collision. | `server/sim/scenarios.js` |
| 38 | Estimated fuel follows the spec formula (L/h = 2 + 0.25 x engine_load x rpm / 2000), burnt only while the engine runs (rpm > 0), integrated between readings at most 15 s apart (the stale time); a longer gap is not guessed. The estimate starts from a full tank when the server starts, so it resets with the server like the rest of the in-memory data. Litres used, km/L and fuel burnt idling come from the same model for every truck (ESTIMATED), including trucks with a fuel sensor. | `server/engine/fuel.js`, `server/config/rules.js` |
| 39 | A `fuel_level` reading replaces the estimate and resets it, so if the sensor drops out the estimate continues from the last measured level. Theft and refuel detection run on measured levels only, over consecutive readings at 0 km/h: a drop of more than 5 % within 60 s is a possible theft; a rise of more than 5 % within 60 s (your pick) is a refuel. Two readings in a row must be past the limit (one could be a sensor glitch, which is then ignored). An event grows while the level keeps moving the same way and ends after 60 s without change, when the truck moves (theft), or when the opposite event starts. A device clock reset closes what was open and restarts the comparison. | `server/engine/fuel.js` |
| 40 | Simulated TN01 has a fuel level sensor (your pick); TN02 to TN05 do not, so their levels are estimated. TN01 starts full, burns at the same rate as the estimate and is refilled at the depot at 0.5 % per second when below 25 % (demo values), which shows up as a detected refuel. | `server/sim/simulator.js` |
| 41 | A refuel logged by the fleet manager raises the estimate by its litres, up to a full tank at the time it is logged, only if it happened after tracking began (earlier ones are already in the full tank the estimate starts from) and the truck has no fuel sensor reading (a measured level is never overridden). Litres must fit the truck's tank. The simulated sensor always uses a 300 L tank. | `server/services/fuel.js`, `server/services/registry.js` |
| 42 | The fuel theft scenario slows TN01 at 3 km/h per second, parks it with the engine off (so the stop is not idling) and drains 0.4 % per second for 30 s (about 36 L), then drives on. It refuses trucks without a fuel sensor. | `server/sim/scenarios.js` |
